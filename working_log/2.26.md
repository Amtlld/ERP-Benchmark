今天首先需要完成数据集的预处理工作。遵循以下流程：
1. 使用Benchmark数据集自带的MATLAB代码进行数据预处理，并保存为.mat文件
    - 带通滤波 (5-90 Hz) 和陷波滤波 (50 Hz)
    - 降采样 (200 Hz)
2. 使用Python代码读取.mat文件，并保存为.npy文件

3. 修复了模型训练 OOM 显存溢出问题
    - 发现原版 Benchmark 在 `FullAttention` 和 `DifferenceAttention` 的前向传播中，基于 `torch.einsum` 构建了完整的 `(Batch, NumHeads, SeqLen, SeqLen)` 注意力矩阵 `scores`，这在大 Batch Size (128) 和长序列下导致了 20GB+ 的庞大显存占用分配，直接引发 CUDA Out Of Memory 报错。
    - 在 `layers/SelfAttention_Family.py` 中增加了对 PyTorch 2.0+ 原生特性 FlashAttention (`torch.nn.functional.scaled_dot_product_attention`) 的调用支持：在不强调输出注意力分数分布矩阵 (`output_attention=False`) 的常规训练场景中，使用低显存、高速度的原生内核替代原始 Python 层的 einsum 和 softmax。
    - 成功将 128 批大小下的极大内存占用压榨至单卡 8GB/24GB 承受范围内，目前跑通了首个 Epoch，单轮步时耗时也有所改善。

4. 优化了数据加载精度以提升计算效率并缩减内存：
    - 发现原版项目中由于使用 Python 内置且并未显式指定数据类型的 Numpy，在调用 `np.load()` 加载保存好的预处理 `.npy` 数据特征和标签时，系统默认将其认定为最高精度的 `float64` 进行内存缓存。但对于分类任务和使用了 FP32 的神经网络模型而言，`float64` 张量在传入 `dataloader` 转换为 Tensor 时不仅会大量由于没必要的精度占据内存，同时后续每一步都可能触发隐式的从 `float64` 到 `float32` 的慢速转化过程，在数据搬运 CPU 到 GPU 期间也很浪费带宽。
    - **修改 1**：在基础数据集加载模块 `data_provider/uea.py: load_data_by_ids` 中直接显式强制追加 `.astype(np.float32)`，在数据加载 IO 阶段就直接丢弃冗余位数，保证整个生命周期被更小更快的 `float32` 取代。
    - **修改 2**：在数据集包装器 `data_provider/dataset_loader/benchmark_loader.py` 和泛化包装器 `data_provider/data_loader.py`（针对混合数据集 `MultiDatasetsLoader`）模块的 `__getitem__` 最终数据抛出环节，在通过 `torch.from_numpy()` 返回之前添加 `.float()` 的硬性保证，杜绝在不小心的多层包装环节再次混入并被还原为双精度张量。
    - **修改 3**：在主控文件 `run.py` 最顶端注册了激活 PyTorch 内部针对 TensorFloat-32（TF32）的高速机制代码：`torch.set_float32_matmul_precision('high')` 及其配套参数。这能全面榨干由于显存降载和浮点格式修复而释放出可用计算瓶颈的 Ampere/Ada Lovelace 架构的 RTX 显卡极速矩阵单元。首个 Epoch 的单纯训练耗时经过简单比对下降了大约 1 秒左右（测试批次从 ~26.7s 降至 ~25.7s）。
